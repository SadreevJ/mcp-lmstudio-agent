# ТЗ на развитие проекта `mcp-lmstudio-agent`

## 1. Контекст и цель

Проект `mcp-lmstudio-agent` уже является рабочей базой для локальной офлайн-разработки с LLM: управление активным проектом, файловая память, brief для новой сессии, синхронизация MCP-конфига, интеграция с LM Studio.

Цель следующего этапа развития:
- превратить проект в сильный, предсказуемый и удобный инструмент локальной разработки кода без интернета;
- ориентироваться не на чат, а на практический coding workflow по директории проекта.

Главный фокус:
- работа с кодовой базой через директорию;
- быстрый вход модели в контекст проекта;
- безопасное и предсказуемое выполнение типовых шагов разработки;
- минимально необходимая автоматизация без архитектурного перегруза;
- сохранение простоты запуска и сопровождения.

## 2. Что считаем успехом

После выполнения этапов проект должен:
- лучше понимать структуру проекта (быстрее находить релевантные файлы, лучше готовить стартовый контекст);
- лучше поддерживать coding workflow (поиск по проекту, запуск проверок, ясный цикл `изменил -> проверил -> зафиксировал контекст`);
- лучше работать как локальный терминальный агент (без IDE, через директорию, shell, MCP и краткие рабочие промпты);
- сохранить текущие архитектурные достоинства (маленький понятный код, разделение ответственности, без тяжёлых агентных фреймворков).

## 3. Жёсткие ограничения разработки

Архитектура:
- не ломать существующую простую архитектуру без прямой необходимости;
- предпочитать локальные изменения вместо большого рефакторинга;
- держать доменную логику отдельно от инфраструктуры;
- не тащить в `domain` зависимости на внешние сервисы/фреймворки/MCP-клиенты.

Кодстайл и инженерные ограничения:
- не выдумывать библиотеки, API и возможности;
- не плодить вспомогательные файлы без явной необходимости;
- не использовать `print` для runtime-поведения, только `logging`;
- не делать скрытых побочных эффектов;
- валидировать входные данные рано и явно;
- не усложнять через абстракции на вырост.

Область работ:
- не включать демонизацию, фоновые сервисы, GUI-упрощение запуска и прочие UX-эксперименты;
- сейчас работаем над ядром локального coding workflow.

## 4. Стратегия развития

Развивать проект поэтапно так, чтобы каждый этап:
- давал практическую пользу сам по себе;
- не блокировал следующие этапы;
- не требовал заранее строить сложную универсальную платформу.

Приоритет:
1. усилить поиск и навигацию по проекту;
2. усилить контекст и память;
3. усилить рабочий цикл разработки;
4. затем улучшать более умные сценарии.

## 5. Этапы работ

### Этап 1. Усиление проектного индекса и навигации
Цель: ускорить ориентацию в кодовой базе и улучшить выбор стартовых файлов.

Ключевые задачи:
- расширить `index.json` полезными метаданными (размер, тип, текстовый/нетекстовый, важность, mtime, приоритет загрузки);
- улучшить эвристику `files to open first`;
- точнее учитывать entrypoints (`README`, `pyproject.toml`, `package.json`, `requirements.txt`, `CMakeLists.txt`, `.env.example` и т.д.);
- не смешивать слои application/infrastructure.

DoD:
- индекс расширен без ломки CLI-потока;
- изменения локальные, без лишних сущностей;
- brief использует улучшенный индекс.

### Этап 2. Поиск по проекту как отдельная capability
Цель: добавить быстрый и предсказуемый поиск по проекту.

Ключевые задачи:
- поиск по имени файла, строке/паттерну, TODO/FIXME, entrypoints, базовым эвристикам определения/подозрительных участков;
- опора на системные возможности и простой shell workflow;
- чёткая граница: поиск = infrastructure, интерпретация = application;
- безопасность: ограничение активным проектом, отсутствие destructive side effects.

DoD:
- поиск встроен в текущий поток;
- не требует IDE-контекста;
- пригоден как часть brief/workflow.

### Этап 3. Усиление проектной памяти
Цель: сделать память полезной для разработки, а не только для заметок.

Ключевые задачи:
- сохранить текущие файлы памяти и расширить структуру только при реальной пользе;
- определить роль каждого memory-файла;
- улучшить обновление summary/решений/проблем/оперативной информации;
- избежать мусора и дублирования.

### Этап 4. Улучшение briefing-механизма
Цель: ускорить старт новой сессии и приблизить к реальному coding workflow.

Ключевые задачи:
- переработать структуру brief под практические вопросы (что за проект, как запускать/проверять, что читать сначала, ограничения, известные риски);
- улучшить выбор правил (global/language/project);
- добавить полезные секции (entrypoints, команды, ключевые директории, риски, последние решения);
- держать brief насыщенным, но компактным.

### Этап 5. Цикл `изменил -> проверил -> зафиксировал`
Цель: сделать разработку менее хрупкой и более воспроизводимой.

Ключевые задачи:
- формализовать post-change цикл;
- безопасно запускать проверки через текущий shell-подход;
- учитывать результаты проверок в контексте/памяти;
- не строить CI внутри проекта и не добавлять магии.

### Этап 6. Git-aware контекст и рабочая осведомлённость
Цель: добавить lightweight-понимание состояния рабочей директории.

Ключевые задачи:
- учитывать изменённые/новые файлы и, опционально, ветку;
- использовать в brief/приоритете чтения/фиксации сессии;
- не превращать в git-оркестратор;
- не добавлять опасные операции по умолчанию.

### Этап 7. Финальная шлифовка CLI-flow
Цель: сделать путь пользователя коротким и понятным без смены философии проекта.

Ключевые задачи:
- пересмотреть UX команд: `bootstrap`, `index-project`, `rebuild-context`, `sync-mcp`, `brief`, `status`;
- привести сообщения CLI к единому тону;
- повысить предсказуемость базового сценария.

## 6. Порядок выполнения

1. Индекс и навигация
2. Поиск по проекту
3. Проектная память
4. Briefing
5. Цикл проверки
6. Git-aware контекст
7. CLI-шлифовка

Причина порядка: сначала лучше видеть проект, затем лучше помнить, затем лучше работать, и только после этого шлифовать ergonomics.

## 7. Роли для новой сессии

Роли как режимы работы:
1. Архитектор
2. Инженер application-layer
3. Инженер infrastructure-layer
4. Инженер DX/CLI
5. Ревьюер/контролёр качества

Базовый self-check перед/после существенных изменений:
- не выдумано ли поведение;
- нет ли лишних файлов;
- не нарушены ли границы слоёв;
- понятны ли имена;
- нет ли скрытой магии;
- нет ли ненужного усложнения.

## 8. Формат работы в следующей сессии

Общие правила:
- один этап за раз;
- сначала анализ текущего кода, потом минимальный план, затем код;
- без пакетных рефакторингов на полпроекта;
- без новых зависимостей без необходимости;
- не создавать новые файлы, если можно чисто встроить в существующую структуру.

Обязательный формат ответа агента на каждый этап:
1. Что сейчас есть в коде.
2. Что мешает целевой функциональности.
3. Минимальный набор изменений.
4. Какие файлы будут изменены.
5. Какие инварианты нельзя сломать.
6. Код.
7. Краткий self-check по rules.
